The `review.gate_severity` map in `chupa/config.py` takes any string as a key. A misspelled gate code loads without error and `gates.merge_severity` merges it into the severity map, where no gate ever looks it up. The operator's intended override then does nothing, and nothing tells them. The proposal is to check keys against `gates.ENGINE_GATE_CODES` when the config loads.

The gap is real but nothing shows it doing harm. Every engine code defaults to `hard` (`DEFAULT_GATE_SEVERITY`), so a misspelled key leaves the real gate at `hard`. The failure is stricter than the operator wanted, not looser, and no gate is skipped or weakened. No incident shows an operator losing an override this way. This is load-time validation hardening of the same kind as decision-box-000030-f689a116 (the auth-name pattern) and decision-box-000026-8732a7a8 (cross-key ordering). It also raises an import-layering question (config importing from gates) that the note leaves open. Reopen if an operator reports that a `gate_severity` override silently did not apply, or if severity values other than `hard` become the default so that a dead key could weaken a gate.

- chupa/config.py:148 `gate_severity: dict[str, Severity] = {}` has no key validation
- chupa/gates.py:90-93 `merge_severity` overlays the overrides on `DEFAULT_GATE_SEVERITY` with no key check, so an unknown key becomes an unused row
- chupa/gates.py:32 every engine code defaults to `hard`, so a misspelled override fails toward the stricter setting
- chupa/tickets.py:44 already validates gate codes against `ENGINE_GATE_CODES` for tickets, so a paved road exists if this is reopened
- No open ticket, merged stem, or registry entry covers gate_severity key validation
