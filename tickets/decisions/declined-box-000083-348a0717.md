A bootstrap note warned that no code wrote terminal `state_transition` events, so `run_seq` stayed 0 for every stem. A second run of the same ticket and attempt in a shared state directory would then replay the first run's recorded LLM calls. It expected the `run <stem>` verb, which writes terminal events, and reconcile-on-entry, which cleans up orphaned runs, to close the gap. Both exist now, and `run_seq` is worked out from the terminal events in the journal.

The gap the note describes is gone. `chupa/journal.py:104` defines `run_seq(events, stem)` from the journal's terminal events. `chupa/runner.py` imports `TERMINAL_STATES` and uses `run_seq(history, ticket.stem)` as the attempt number, so it rises after each terminal event. `chupa/reconcile.py` and `chupa/serve.py` use that same count when they check what a run has kept. `Driver` (`chupa/driver.py:259`) gets the sequence from the journal. A re-run after a terminal event therefore gets a new key and does not replay old calls. The note shows no current harmful behavior.

- chupa/journal.py:104 defines run_seq(events, stem)
- chupa/runner.py:28,163,175 imports TERMINAL_STATES and passes the journal-derived run_seq into the LLM effect key
- chupa/reconcile.py:11,22 does reconcile-on-entry using TERMINAL_STATES and run_seq
- chupa/driver.py:259 gets seq from journal_run_seq when no explicit run_seq is given
- chupa/llmeffect.py:3-4 says replay happens only on same-key re-entry with no terminal event in between
