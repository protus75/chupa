`Journal.append` in `chupa/journal.py` (line 185) calls `os.write` once and ignores how many bytes it wrote, then fsyncs and reports success. If the disk fills partway through a write, the caller believes a torn record is durable. The next append skips the once-per-handle tail repair and writes after the torn line, leaving a malformed line in the middle of the segment.

The code gap is real: one unchecked os.write, and tail repair runs only once per Journal instance (`_tail_repaired`). But the failure needs a partial write on a local regular file. On Linux that happens only when the disk fills or the file size limit is hit partway through a record of a few hundred bytes. The message is a bootstrap-ingest note, not an observed failure. Nothing shows a torn mid-segment record, a mid-segment JournalCorruption error, or a full disk on a state directory. Under the earning-incident rule this is speculative hardening against a condition nobody has seen, which matches how the registry handled the journal-seam note in decision-box-000003-8007f56c. No open or merged ticket covers it (harden-journal-roll-1 and journal-roll cover rolling segments, not short writes), so it is not a tombstone.

- chupa/journal.py:183-188 opens the file with O_APPEND, calls os.write(fd, data) once without checking the returned byte count, then fsyncs and returns the event.
- chupa/journal.py:177-179: _truncate_torn_tail runs only while self._tail_repaired is False, so a later append on the same handle does not trim a torn tail before writing.
- chupa/journal.py:194: read_segments drops a torn line only at the end of the active segment, so a torn line in the middle of a segment is not tolerated on read.
- The message's origin is bootstrap-ingest, with no stage, outcome, failure report, or run evidence of a short write or mid-segment corruption.
- decision-box-000003-8007f56c set the bar for journal-seam hardening: no incident means a decision.
