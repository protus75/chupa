The spec linter and the spec renderer treat line breaks differently. `_parse_spec` and `_blocks` in `chupa/specs/__init__.py` split with `str.splitlines()`, which accepts `\r\n` and lone `\r`. The renderer's `_PLACEHOLDER_LINE` regex is MULTILINE, so its `$` matches only before `\n`. If spec text with a `{{name}}\r\n` placeholder line reached `load_spec` directly, lint would pass it and `render` would leave the placeholder in place without inserting the payload.

The mismatch is real only for text that has not passed through file loading. It cannot happen at runtime because every production caller reads a spec with `Path.read_text()`, whose default newline handling turns `\r\n` and `\r` into `\n` before `load_spec` sees the text. The repro builds a string in memory and skips that path. All tracked spec files use LF. No run has been shown to render a prompt with a placeholder left in or a payload dropped. That makes this hardening plus a test, with no harmful behavior that can actually be reached.

- chupa/specs/__init__.py:38 `_PLACEHOLDER_LINE = re.compile(rf"^\{{\{{({_NAME})\}}\}}$", re.MULTILINE)` — `$` anchors before `\n` only
- chupa/specs/__init__.py:178 `lines = body.splitlines()` feeds `_blocks` (line 182), which accepts `\r\n`
- Every load_spec caller reads with default universal newlines: stages.py:380, retro.py:325, requisition.py:58/89, rework.py:85, baseline.py:44, author.py:194, policy.py:28, triage.py:107, __main__.py:683 all use `Path.read_text()`
- `git ls-files --eol chupa/specs` reports no non-LF spec files
