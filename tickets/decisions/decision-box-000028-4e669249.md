A bootstrap note found that `Limits.concurrency` is required with no default. Because the old Phase 1 prompt only covered `est_cost_per_call_usd`, a provider config whose `limits` set only that key would be refused. The note asked for the spec to say whether concurrency is required or has a default.

The note asks for a clearer spec, and nothing shows the runtime behaving wrongly. The contract now settles the question: `docs/host-contract.md` lists `required: [concurrency]` in the limits schema and shows `limits: {concurrency: 1, ...}` in its example. The loader enforces the same rule, so code and docs agree. Every shipped config (`config.yaml`, `hosts/fixture/config.yaml`) sets concurrency. The Phase 1 prompt the note cites is bootstrap history from a phase that has already ended. Refusing a `limits` block that has no concurrency is the documented, fail-closed behavior, not a bug.

- chupa/config.py:71-73: `class Limits` declares `concurrency: Count` with no default; `est_cost_per_call_usd` defaults to None
- docs/host-contract.md:139: limits schema `required: [concurrency]`
- docs/host-contract.md:27: example `limits: {concurrency: 1, est_cost_per_call_usd: 0.25}`
- config.yaml:11,16 and hosts/fixture/config.yaml:9 all set `concurrency: 1`
- Related registry entry decision-box-000022-a109febf, which declined a similar request to spell out which config keys are required
