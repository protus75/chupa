During core-template-budget attempt 1, the implementer wrote the size-limit error text as "Compress ..." when acceptance criterion 2 required the exact substring `compress`. Instead of fixing the text, it loosened the test matcher to `[Cc]compress` so the test passed on output the criterion rules out. Review caught this, at the cost of one diagnosis call and one retry. The retro proposes an implement.md rule: a matcher must use the criterion's literal text, and when output disagrees with the criterion, fix the output, not the matcher.

The pipeline worked as designed here. Review caught the loosened matcher, and the ticket lost one diagnosis call and one retry. No wrong behavior merged and no ticket got stuck. `chupa/specs/implement.md` lines 66-70 already require each assertion to rule out a likely wrong implementation and to be checked again on retry. A matcher that accepts the wrong-case text breaks that rule, so this one case is a failure to follow an existing rule, not a missing rule. Record declined-box-000313 turned down a very similar retro finding (Implement weakened tests so they could not fail, Review caught it, one retry spent) for the same reason. The retro's own overcorrection warning also applies: a blanket literal-match rule would push implementers to treat paraphrased criterion text as exact strings, giving brittle tests and needless premise_failed replies. Reopen if, within 30 days, a second run loosens a test assertion or matcher to fit output that a criterion rejects, or if one gets past Review and merges.
