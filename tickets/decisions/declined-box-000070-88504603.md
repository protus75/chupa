When a provider call is aborted during the short gap between starting the CLI process (`create_subprocess_exec`) and recording its process group (`on_spawn`), `ProviderLLM.abort_current` finds no process group to kill. Only the cancellation that follows stops the process, and asyncio's transport close kills just the direct child, not its whole group. The note suggests a pending-abort flag that the spawn path checks.

This is speculative hardening, not a demonstrated behavior gap. The window covers only the await on `create_subprocess_exec`. `on_spawn(proc.pid)` runs synchronously as soon as that await returns, before any reader or timeout await. During the window the child has only just been exec'd, so it is very unlikely to have started grandchildren that would outlive a kill of the direct child. The note itself calls the window sub-millisecond, and it reports no incident, orphaned process, or failed run. The abort path still ends the call: the cancellation that follows unwinds `invoke`, and once the pgid is published, `SubprocessExec.run` group-kills through `_kill_and_wait` on cancellation. Nothing here gives a post-change observation that reachable runtime behavior is wrong.

- chupa/seams.py:113-136: `create_subprocess_exec(..., start_new_session=True)` is followed directly by `on_spawn(proc.pid)`, with no intervening await
- chupa/seams.py:147-152: after spawn, any BaseException (including cancellation) group-kills via `_kill_and_wait` -> `kill_group(proc.pid)`
- chupa/providers.py:627-629: `abort_current` is a no-op when `_active` is None or the adapter has no pgid yet
- No incident, orphaned-process report, or failed run is cited; the note calls the window sub-millisecond
