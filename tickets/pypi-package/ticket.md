## Goal / Why
A host should install chupa with `uv tool install chupa` and run `chupa <verb>`, instead of running `python -m chupa` from a chupa checkout. The VS Code extension, published to the VS Code Marketplace, needs that installed command to exist (2026-11-06). Today `pyproject.toml` has no `[build-system]` and no console script, so `uv build` cannot produce an installable wheel. The `chupa` project exists on PyPI with no files: a broken `0.1.0` upload was deleted, and PyPI never accepts a file name twice, so the first release must be a new version (2026-11-06).

After this change:
- `uv build` produces a wheel that carries `chupa/specs/` and installs a `chupa` command that runs `chupa.__main__:main`;
- `./dev.py publish` builds and uploads that release.

## Scope in / Scope out
- In: `pyproject.toml`:
  - `[build-system]` with `requires = ["uv_build>=0.11.32,<0.12"]` and `build-backend = "uv_build"`;
  - `[tool.uv.build-backend]` with `module-root = ""`, because the package sits at the repo root rather than under `src/`;
  - `[project.scripts]` with `chupa = "chupa.__main__:main"`;
  - `version = "0.1.1"`, a one-time bump past the deleted `0.1.0`.

  `uv.lock` is regenerated by `uv lock`.
- In: `tests/test_cli.py`: `test_project_stays_virtual` asserts the opposite of this change, so it is replaced by a test that `pyproject.toml` declares `build-backend = "uv_build"` and `[project.scripts]` `chupa = "chupa.__main__:main"`.
- In: `dev.py` gets a `publish` subcommand. It refuses with a message naming `UV_PUBLISH_TOKEN` when that variable is unset. Otherwise, in a temporary directory, it runs `uv build -o <tmp>`, then `uv publish` with the built files as explicit paths (argv lists, through the existing `run` helper). The version comes from `pyproject.toml` and is never bumped by the command. The module docstring's usage lines and `--help` list it.
- In: docs.
  - `docs/how-chupa-works.md` section 2: an installed engine runs as `chupa <verb>`, and a checkout as `uv run python -m chupa <verb>`.
  - Section 2.2: a `publish` row.
  - `docs/host-contract.md` `## Instance custody`: a stable instance is a PyPI release installed with `uv tool install chupa==<version>`; upgrade and rollback reinstall a version.
  - `README.md`: one install line.
- Out:
  - git tags and pushes;
  - the license: `LICENSE` and the `license` and `license-files` fields in `pyproject.toml` are already set and stay unchanged;
  - any version bump beyond `0.1.1`;
  - the VS Code extension;
  - CI publishing;
  - engine behavior.

## Acceptance criteria
1. The wheel built by `uv build --wheel` contains `chupa/specs/review.md` and an entry point `chupa = chupa.__main__:main`, contains no `tests/` or `eval/` file, and is named `chupa-0.1.1-*.whl`. The first Verification command checks this.
2. `uv run chupa --help` exits 0, so the console script is installed.
3. With `UV_PUBLISH_TOKEN` unset, `./dev.py publish` exits non-zero and its output names `UV_PUBLISH_TOKEN`, without running `uv build`. The third Verification command checks this.
4. `tests/test_dev.py::test_publish_uploads_built_files` sets `UV_PUBLISH_TOKEN` and fakes `dev.subprocess.run`, the fake writing a wheel and an sdist into the `-o` directory on the build call. `./dev.py publish` then makes exactly two calls: `["uv", "build", "-o", <tmp>]`, then `["uv", "publish", <each built file>]` as argv lists. It runs no git and leaves `pyproject.toml` unchanged.
5. `docs/how-chupa-works.md` sections 2 and 2.2, `docs/host-contract.md` `## Instance custody`, and `README.md` describe `chupa <verb>`, `uv tool install chupa`, and `./dev.py publish`.
6. `uv run pytest -q` exits 0.
